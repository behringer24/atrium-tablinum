# Changelog

All notable changes to Atrium Tablinum. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). How a release is made is described in [docs/release.md](docs/release.md).

## [Unreleased]

### Changed
- **Curator and space admin tools are listed for everyone:** `review_knowledge`, `review_skill`, `publish_skill`, `block_skill`, `unblock_skill`, `space_members`, `space_add_member` and `space_remove_member` are in the tool list of every logged-in user. Assistants read the list once and keep it, so a user who was made curator or space admin later did not see the new tools until they reconnected. Whoever does not hold the role yet gets a compact form (one sentence naming the role, parameters without their texts), which keeps the longer list cheap; the role is still checked on every call. The instance admin tools stay limited to instance admins.

## [0.5.0] - 2026-11-10

### Added
- **Export of knowledge:** the new tool `export_knowledge` prepares a ZIP of Markdown files, one folder per space, one file per entry with a YAML header, and an `index.md` per folder. The archive follows the Open Knowledge Format (OKF) version 0.2: the header carries `type`, `title`, `tags`, `status`, `stale_after` and `generated`, the root `index.md` names `okf_version`, and everything else (author, owner, version, dates, exact state) is under the key `atrium`. It returns a link that works for ten minutes and once (`GET /export/<token>`, signed, checked again when opened). Admins export a space or all team spaces they administer, instance admins every team space, everybody their own personal space; nobody can export someone else's personal space. Entries in every state are included, older versions, handoffs and skills are not. Every export is in the audit log as `knowledge_export` with the number of entries.
- **Guide for Pro licensees:** `docs/pro/pro-edition.md` (with PDF) describes what a licensee needs: reading, installing, renewing and removing the licence, what `not covered` and the reminders mean, the user limit and the guided offboarding with `admin_transfer_personal_space` and `reassign_owner`.
- **Build from source:** `docs/release.md` describes how to build the Community edition from a checkout, with Docker or with Go.
- **Instance names at runtime:** the short name users say in a chat and the organisation name are read from `config.yaml` on the first start only, stored in the database and from then on changed by an instance admin with the new tool `admin_instance` (`get`, `set` with confirmation, audited as `admin_instance_set`), without a restart; new connections see the change. The server instructions now name the organisation too, so assistants connected to several instances can tell them apart. The product name stays in the configuration.
- **Defaults for environment variables in `config.yaml`:** `${VAR:-default}` uses the default when the variable is unset or empty; `${VAR}` stays mandatory. The shipped `config.example.yaml` reads the instance names from `ATRIUM_SHORT_NAME` and `ATRIUM_ORGANIZATION_NAME`, which `docker-compose.yml` passes on from `.env`, so a basic setup needs no change to the YAML.

### Changed
- **A basic setup needs only `.env`:** `config.example.yaml` now reads `instance.base_url` (`ATRIUM_BASE_URL`), the login domain (`ATRIUM_ALLOWED_DOMAIN`) and `bootstrap_admins` (`ADMIN_EMAIL`) from the environment, which `docker-compose.yml` passes on from `.env`. They are mandatory: the server refuses to start and names the missing variable, so nobody runs with a placeholder address or admin. Private accounts without a domain keep using `allowed_emails` in `config.yaml`. An existing `config.yaml` is not touched.
- **User guides:** the introduction gains a section "What it takes to run" (free Community edition, parts, memory, prerequisites), a point on working from any device without syncing, a note on how rights are enforced inside the search and an honest note on the context that tool descriptions use. The user guide explains how much one search returns, the curator guide answers who decides what is still valid, and the embedding page says that search is hybrid.
- **Public texts say what Community is and no more:** the editions page, the instance admin guide, the offboarding notes, the configuration example, the workflow and code comments no longer describe the Pro internals. The build notification of `.github/workflows/test.yml` now reads its target from the repository secret `BUILD_NOTIFY_URL` (no value, no notification).
- `docs/staging.md` no longer lists re-embedding as missing (`admin_reembed` exists since 0.4.0).

### Upgrade notes
- No database migration. An existing `config.yaml` keeps working; the instance names in it are stored in the database on the first start of this version and from then on changed with `admin_instance`.
- A `config.yaml` that uses `${VAR:-default}` needs this version: older ones take the text literally.

## [0.4.0] - 2026-11-07

### Added
- **Changing the embedding model** (migration 12): vector search and the duplicate check use only vectors of the configured model; sections of another model are found by full text until they are rebuilt. New tool `admin_reembed` (instance admin): `status` shows how many sections are not embedded with the configured model, `start` (after confirmation, audited) rebuilds them in the background with the periodic task `reembed`, batch by batch and across restarts, `stop` pauses it. `admin_health` has an informational check `embeddings`, and the server log warns at start. A model with another dimension needs the new setting `embedding.allow_dimension_change: true` for one start, which rebuilds the vector column and drops every vector (contents stay). See [docs/embedding.md](docs/embedding.md#dimension-and-changing-the-model).
- **Knowledge types, responsible people and review dates** (migration 11): an entry has a `type`, `rule` (binding), `documentation` (default), `recommendation` or `experience`, shown in search hits, entries, lists and `whats_new` and filterable (`search_knowledge types`, `list_knowledge type`); assistants are told to name it, a rule being binding and the last two not. Only curators and admins of a team space set or remove `rule` and change or move an entry of type rule, also in spaces without approval; the type is recorded in every version. An entry can name a responsible person (`owner`, team spaces, active and able to read the space; never derived from the author) and a review date (`review_due`); overdue reviews show as `review_overdue`, in `list_knowledge review=due` and as `reviews_due` per space in `whats_new` for curators, and nothing is hidden or deleted. Changing only these two writes no version. New tool `reassign_owner` (space admins for their spaces, instance admins for all team spaces, with confirmation) hands every entry of one person to another, skipping spaces the new person cannot read; audited as `owner_reassign`. See [docs/design/knowledge-metadata.md](docs/design/knowledge-metadata.md).
- **Support information:** new tool `admin_support_bundle` (instance admin) collects what a support request needs: version and build, health, Go, Postgres and pgvector versions, migration, database size, counts of users, spaces, entries and skills, and the settings of `config.yaml` by a fixed list (`config.SupportSummary`). No content, no names of people or spaces, no secrets; audited as `support_bundle`. See [docs/user/05-instance-admin.md](docs/user/05-instance-admin.md).
- **What is new:** new tool `whats_new` lists the entries of the team spaces a user can read that were published (`new`) or changed (`updated`) since a date (default: the last 7 days), and the skills released since then; curators also see how many drafts and skill drafts wait in each space they curate. Only what the caller may read appears; drafts, archived entries and personal spaces never do. See [docs/user/01-user.md](docs/user/01-user.md).
- **Canary builds:** every push to the `dev` branch builds an image tagged `canary` (moving) and `canary-<short sha>` (immutable), never `latest` or a version tag. `server_info` reports the canary version. See [docs/release.md](docs/release.md).
- **Skill registry:** Atrium distributes skills, approved working instructions in the Agent Skills layout (`SKILL.md` plus text files), as a kind of its own, separate from knowledge entries. Versions are immutable once released and carry a SHA-256 digest; review, publishing and blocking are separate steps, a curator other than the author must approve, and class C skills can only be published by an instance admin. New tools: `list_skills`, `get_skill`, `get_skill_resource`, `store_skill`, `review_skill`, `publish_skill`, `block_skill`. Released skills are announced in the per-user instructions. Text only: scripts and binary files are refused and Atrium runs nothing. See [docs/skills.md](docs/skills.md).
- **Skills now have the same life cycle tools as knowledge entries:** `archive_skill` and `unarchive_skill` hide a whole skill from everyone who cannot restore it (`list_skills archived=true` shows the archive), `delete_skill` removes a skill with all versions for good (only instance admins in a team space, the owner in a personal space; the audit log keeps name and digests), and `unblock_skill` lifts a block (space admins and instance admins, reason required). An unblocked version is approved again, not released. See [docs/skills.md](docs/skills.md).
- New setting `skills.allow_self_approval` (default `false`) for installations with a single curator.
- **Shipped skills for the care of the knowledge base:** `skills/knowledge-ingest` turns a source the user provides into entries (compares with what Atrium knows, proposes new entries and updates, saves what the user confirms) and `skills/knowledge-lint` checks a space for outdated entries, duplicates, contradictions, broken references, sensitive content and waiting drafts. Both use only the knowledge tools, never delete or approve, and change nothing without confirmation. Atrium does not install them: an organisation stores, reviews (class B) and releases them like its own skills. Tests check that both are valid packages and name only tools and parameters of the build. See [skills/README.md](skills/README.md).
- **MCP Skills extension (SEP-2640):** Atrium declares `io.modelcontextprotocol/skills` and serves released skills as resources (`skill://<space>/<skill>/<file>`, `skills/list`, `skills/get`, `resources/read`) with digest and size per file, so clients that support the extension can load them like their own skills. Same rights, release, archive and block rules as the tools, which keep working for every other client. See [docs/skills.md](docs/skills.md).
- **Skill export:** `GET /skills/export/<space>/<skill>[?version=N]` returns a released version as a reproducible ZIP in the Agent Skills layout, behind the same bearer authentication as `/mcp`. Audited as `skill_export`.
- **Server icon:** Atrium serves an icon at `/favicon.ico` and `/icon` and sends it in the MCP server info. Built-in default; `instance.icon_file` sets an own image. See [docs/deployment.md](docs/deployment.md).
- **Branded PDFs:** every PDF of the user guides carries the same branding (Atrium icon and the behringer24 logo with "behringer24 – Andreas Behringer" in a header on every page and a footer with the page number).
- **Why Atrium:** a persuasive but honest introduction (`docs/user/00-why-atrium.md`) for everybody who is to adopt Atrium: what it brings individuals, teams and the organisation, one memory across assistants, a day with Atrium, a first ten minutes, the limits, and a rollout plan. To share before the guides.
- **User guides:** five English guides in `docs/user/` for everyday users, authors, curators, space admins and instance admins, covering the functions for knowledge and skills, the daily workflows and processes and a FAQ each, with an index. Markdown is the source; `scripts/build-docs.sh` builds a PDF next to each guide (Node.js and Chrome or Edge needed).
- **Audit shows the route of a skill read:** the details of `skill_get`, `skill_resource` and `skill_export` carry `via` (`tool`, `resource`, `rpc`, `export`), and `skills/list` is logged as `skill_list`. New setting `instance.log_level` (default `info`); `debug` adds one log line per MCP request. See [docs/skills.md](docs/skills.md).
- **Skill tags and filters:** skills have tags like knowledge entries (`store_skill tags`, new tool `tag_skill`; they belong to the skill, so retagging needs no new version). `list_skills` gained `tag`, `query` (text in name, description or tags), `status` (e.g. `draft` for the review queue) and `limit`, and the tags appear in `get_skill` (not in the instructions, see the security notes). See [docs/skills.md](docs/skills.md).
- **Skill quotas:** a personal space is limited to 50 skills and 5 MB of skill files (all versions), and one skill to 100 versions in any space (`skills.personal_max_skills`, `personal_max_bytes`, `max_versions_per_skill`; 0 = unlimited). A save over a limit is refused with the reason. See [docs/skills.md](docs/skills.md).
- **Moving skills and watching them:** new tool `move_skill` files the newest released version of a skill in another space as a draft that the curators there have to review (a release never travels along; the old skill is archived unless `keep_source=true`). `admin_audit_log` can now be filtered by `skill` and by `client`, and moves are audited as `skill_move_out` and `skill_move_in`. See [docs/skills.md](docs/skills.md).
- **Community and Pro editions:** one code base, two editions ([docs/licensing.md](docs/licensing.md)). The **Community** edition (this repository) is for **8 active accounts** (counted as registered accounts active at the same time, not connected assistants; locked accounts do not count) and sends no telemetry. New accounts and the reactivation of a locked one wait while there is no room; existing active accounts are never touched. `server_info` shows the edition and the build date; `admin_health` has an informational `edition` check. No state blocks or deletes content.
- **Quotas an instance admin changes at runtime:** new tool `admin_quotas` shows and sets the five storage limits (entries, bytes, skills, bytes of skill files, versions per skill) for all personal spaces, all team spaces, one user's personal space or one team space. The most specific level wins, each field on its own, `0` is unlimited and `-1` inherits again. A change applies to the next write, needs no restart and survives one; it is audited as `admin_quota_set` with the old and new values. `get` shows where each value comes from and the usage; space admins see limits and usage of their space in `space_members`. Team spaces are limited too now (defaults per space: 5000 entries, 200 MB, 300 skills, 50 MB of skill files, set in `config.yaml` as `spaces.team.*` and `skills.team_*`), so that one author cannot flood a space with drafts. See [docs/user/05-instance-admin.md](docs/user/05-instance-admin.md).
- **Data model overview:** `docs/data-model.html` shows the database after the latest migration as an interactive ER diagram: all 20 tables with columns, types, keys, constraints, indexes (including HNSW and full text), triggers and what each table is for, grouped by area, with search, area filter and highlighted relationships. Self-contained, no network access. `node tools/docs/check-data-model.mjs` compares it with the migrations. See the [README](README.md#development).
- **Slash commands find their skill:** the descriptions of `list_skills` and `get_skill` now start with the hint that a `/name` command such as `/helloworld` is a skill, because clients that load tools on demand show an assistant only the first words of a description before the server instructions arrive.

### Changed
- **Images are built by the maintainer:** the workflow of this repository (`.github/workflows/test.yml`) runs the tests and reports a passed run to the maintainer's build; it no longer builds or prunes images itself, and `cleanup.yml` is gone. Tags of the form `vX.Y.Z` and pushes to `dev` work as before. `docs/release.md` describes the flow.
- **The guided offboarding belongs to the Pro edition:** the Community edition keeps `admin_offboard_user` (locks the account, ends its sessions, deletes its handoffs, reports the personal space and its deletion date) and `admin_reactivate_user`; the responsible person of an entry is changed entry by entry with `update_knowledge`. The tool answers carry the hooks for the extended offboarding. `editionTools` are now called once for every tier of tools.
- Everything is English now: documentation, code comments, tool descriptions, the MCP instructions, error and confirmation messages, log texts and the browser pages of the login flow. Assistants still answer users in the user's language.
- The displayed name of a personal space is "My personal space". The space matcher keeps accepting the German aliases ("mein persönlicher Bereich" and others) and also accepts English ones ("my personal space", "my space", "private").
- Log attribute keys are English (`duration`, `count`, `stored`, `configured`). Adjust log searches and alerts that used the German keys.
- The reason of `login_denied` audit entries is English. Existing entries and stored data keep their German text.

### Fixed
- **A changed TEI model went unnoticed:** TEI takes its model from `--model-id`, and Atrium recorded the name from `embedding.model` with every vector, so changing one without the other stored vectors of one model under the name of another, and `admin_reembed` found nothing to rebuild. With the `tei` backend Atrium now asks the server which model it serves (`GET /info`, at most once a minute) before embedding and with every readiness check. While the names differ, it embeds nothing: saving fails with a hint to tell an instance admin, search falls back to full text, `/readyz` is not ready and `admin_health` (check `embedder`) names both models. Servers that do not name their model are accepted; `embedding.options.check_model: false` switches the check off. See [docs/embedding.md](docs/embedding.md#tei).
- **Former curators were named as contacts:** a locked account keeps its space memberships (so that a reactivation restores them) but has no rights; `space_contacts` and `space_members` now mark such people `former` and list them after the active ones, so that nobody is sent to ask somebody who has left. `admin_offboard_user` also reports for how many entries the person is named as responsible (`responsible_for`).
- **Fewer embeddings on updates:** `update_knowledge` re-indexes an entry only when its title or content changed, not for a change of tags or type.
- **Cleaner package list:** image builds no longer push provenance attestations (two extra untagged entries per build), and after every successful canary build the job `prune` removes older `canary-*` versions with their platform images, keeping the newest three (release tags are never touched). It needs the repository secret `PACKAGES_PAT`; the workflow `cleanup.yml` is the same rule to run by hand, with a dry run. See [docs/release.md](docs/release.md).
- **Instance admins can release their own skills:** the four-eyes rule for skills no longer blocks instance admins from reviewing and publishing a version they wrote themselves. The audit entry `skill_approve` carries `self_approved`. Curators and space admins still need another curator unless `skills.allow_self_approval` is set.
- **Personal space by slug:** the `space` argument now accepts the slug of the caller's own personal space, which `choose_space` offers but was rejected before, so an assistant could loop on the question. Skill tools also show the personal space as "My personal space" instead of the owner's name.

### Security
- **Skill tags no longer reach the instructions.** They are set without a review (by the creator, also later with `tag_skill`), so putting them into the block of "approved working instructions" let an author push unreviewed text into every reader's instructions. The instructions carry the reviewed description only. Tags (of skills and of knowledge entries) must not contain line breaks, control or invisible characters any more, and skill tags are scanned for credentials like entries are.
- **A review approves what the reviewer read.** `review_skill` with `decision=approve` needs the `digest` that `get_skill` returned and refuses the approval if the author rewrote the draft in the meantime. The `skill_approve` audit entry carries the digest. Reject needs none. Clients that approve without a digest get an error telling them to pass it.
- **A transferred personal space brings no unreviewed skills.** `admin_transfer_personal_space mode=space` blocks the released versions the owner had published alone (`skill_block` in the audit log, `skills_blocked` in the result). A space admin lifts the block with `unblock_skill` and a curator releases the version again.
- **Hardening against attacks from outside (second audit):** the HTTP server reads requests within a minute and closes idle connections after two (no more connections held by slow bodies); `/oauth/token` and `/oauth/revoke` are limited to 300 requests a minute per address; a failing token check (for example the database is down) is logged and answered with a fixed text instead of the internal error; the pages of the login flow send `X-Frame-Options`, a restrictive `Content-Security-Policy` and `Referrer-Policy`; `/readyz` answers only `ok` or `not ready` and reuses a result for five seconds; the bundled nginx template sends HSTS.
- **Registrations cannot fill the client table any more:** clients that never completed a login are deleted after an hour (was a day) and only they count toward the cap of 5000, so a flood of anonymous registrations does not block new connections.
- **Redirect patterns are checked:** an `auth.allowed_redirect_uris` entry with `*` must have a `/` before it, and the host of a wildcard entry is compared exactly (`https://host*` also matched `https://host.evil.example/`). A configuration that violates this is refused at start.
- **`dev_mode` needs a loopback listen address** (`127.0.0.1:...`), not only a `base_url` on localhost; otherwise the static dev token was reachable from the network.
- **An approved entry of a space with approval is a curator's to archive.** Authors could archive their own approved entries alone and so take binding content away from all readers; archiving now follows the rule for changing and moving. Authors still archive their own drafts and returned entries, and everything in spaces without approval.
- **A name held by a skill you cannot see is simply taken.** `store_skill` no longer attaches a new version to somebody else's unreleased draft, and neither it nor `move_skill` reveals whether a draft or an archived skill holds the name (the answer is "that name is not available"). The right to retag a skill follows the author of the newest released version, not the first creator.
- **Refused attempts are audited.** A refusal because of the caller's role, a required approval, an own-version approval or a rate limit is recorded as `denied` with the tool and the reason, no arguments, at most once a minute per user, tool and reason. A missing item is not logged.
- **Separate database accounts (opt-in).** `scripts/db-roles.sql` creates `atrium_app` (reads and writes the data, can only append to the audit log, cannot change the schema or switch triggers off) and `atrium_migrate`; `database.migration_url` makes the server migrate with the second and run with `database.url`. The server warns at start while it runs as a superuser. The test suite can run with the restricted account (`ATRIUM_TEST_RESTRICTED=1 go test -p 1 ./...`). See [docs/deployment.md](docs/deployment.md).
- **Front matter ends at a line that is exactly `---`**, as common clients read it; `----` or `--- x` no longer close the block, so Atrium and a client cannot see different names and descriptions for one file.
- **`skills/list` pages by cursor.** A page holds up to 200 skills, one entry each (the newest released version), and carries `nextCursor`; a skill with many versions no longer takes the place of others, in `skills/list`, `list_skills` and the instructions (the listing counts skills, not versions).
- **Admins can delete archived entries directly**, without restoring them first (`delete_knowledge`), which makes removing personal data from the archive one step.
- **Only verified e-mail addresses link accounts or create admins.** The identity now says whether the provider vouches for the address (`email_verified` for Google and OIDC). An unverified address is never linked to an existing account (`auth.link_accounts_by_email`) and never creates the account of a `bootstrap_admins` address; the login is refused and recorded as `login_denied`. Entra sends no such claim, so its addresses count as unverified unless the provider sets the new option `email_trusted: true` (only for a tenant without guests and without self-editable mail attributes).
- **Pinned and checked build:** `go.mod` pins the toolchain (`go1.26.10`, which fixes the 20 standard-library vulnerabilities that `govulncheck` found with 1.26.4), the Dockerfile pins both base images by tag and digest, all GitHub Actions are pinned to commit SHAs, `govulncheck` runs in the test job, and Dependabot opens weekly pull requests for Actions, Go modules and base images. See [docs/release.md](docs/release.md).

### Upgrade notes
- Migration `00007` creates the skill tables and the triggers that freeze released versions. Migration `00008` adds the archive columns and lets a blocked version go back to approved (and only there).
- Migration `00009` adds the tags column to `skills`.
- Skill names held by something the caller cannot see now answer "that name is not available"; clients that showed "the skill is archived" to authors see the new text.
- **Community user limit:** a new instance accepts 8 active accounts. An instance that already has more keeps them all; it simply cannot add accounts (or reactivate locked ones) until it is under the limit.
- Migration `00010` creates the `quotas` table and moves the per-user limits of the `users` table into it. **Team spaces are limited from now on** (defaults: 5000 entries, 200 MB, 300 skills, 50 MB of skill files per space). A team space that already holds more cannot take new content until an instance admin raises its limit with `admin_quotas` or you change `spaces.team` and `skills.team_*` in `config.yaml`; nothing is deleted.
- Operators of an **Entra** provider who rely on `bootstrap_admins` or `link_accounts_by_email` must set `email_trusted: true` on that provider (only for a tenant without guests and without self-editable mail attributes), otherwise those logins are refused. Google and OIDC providers that send `email_verified` are unaffected.
- The server now refuses to start with `dev_mode` on a non-loopback `instance.listen` or with an `allowed_redirect_uris` entry that has a `*` without a `/` before it (see the security notes). `/readyz` no longer says whether the database or the embedder is the problem; look at `admin_health` or the log.

Planned work is listed in the [ROADMAP.md](ROADMAP.md).

## [0.3.0] - 2026-11-03

### Added
- **Archive with restore:** archived entries disappear from the active knowledge base but are kept. Whoever may archive (authors their own entries, curators and admins of the space) can list them with `list_knowledge status=archived`, search only the archive with `search_knowledge archive=true`, and bring them back with `unarchive_knowledge`. A restored author entry in a space that requires approval goes back to review. See [docs/archive-and-context.md](docs/archive-and-context.md).
- **Instance context:** `admin_context` sets a text that tells every connected assistant what this Atrium instance contains. It is shown together with the descriptions of the spaces the respective user may read.
- **Questions users can ask:** `space_contacts` names the curators and admins of the user's spaces, `server_info` the running version (set by the release build).
- **Managing logins:** `my_sessions` and `revoke_my_sessions` for users, `admin_revoke_sessions` for instance admins.
- **Login allowlist at runtime:** `admin_allowlist` manages allowed e-mail domains, single addresses and Entra tenants without a restart. Entries only widen what `config.yaml` allows. Rejected logins appear in the audit log as `login_denied` (with provider and reason, without the address).

### Changed
- Content read from the store is marked as untrusted data, in the results and in the MCP instructions.
- `admin_context` (set, clear) and changing a space description need `confirm=true`. The previous text is kept in full in the audit log.
- Reads are rate limited (`rate_limit_reads_per_minute`, default 120).
- A session ends after `auth.session_max_age` (default 90 days), even if it is used continuously.
- An admin cannot transfer their own personal space to themselves.

### Security
- Accounts are no longer linked by e-mail address automatically. This is only done with `auth.link_accounts_by_email: true` and is then written to the audit log as `account_linked`.
- `dev_mode` only runs with a `base_url` on localhost and a mandatory `dev_token` of at least 16 characters. The token is neither generated nor logged.
- The message shown for a rejected login no longer contains the e-mail address.

### Upgrade notes
- Migrations `00005` (session start) and `00006` (login allowlist) run automatically on first start.
- If you run several login providers that share e-mail addresses, you must enable linking deliberately.
- `dev_mode` needs the new mandatory settings, otherwise the server does not start.

## [0.2.0] - 2026-11-02

### Added
- **Drafts on request:** `store_knowledge draft=true` stores an entry as a draft in any team space, even without required approval and also for admins.
- **Curator review:** `review_knowledge` releases a draft or sends it back with a mandatory note (`review_note`). A revised rejected entry goes back to draft. Curators cannot release their own draft, admins can (marked `self` in the audit log). `list_knowledge` filters by status. See [docs/approval.md](docs/approval.md).

## [0.1.1] - 2026-11-02

### Fixed
- The MCP endpoint serves clients without a session id by running stateless.
- `.env.example` explains how to choose `POSTGRES_PASSWORD`.

## [0.1.0] - 2026-11-02
